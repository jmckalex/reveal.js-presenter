# CLAUDE.md

This file guides Claude Code when a user points it at this directory to add a
second-device presenter view to their reveal.js presentations. The work
happens in **the user's project**; this directory is the reference
implementation, the tests and the record of why it is built as it is. Read
`README.md` for the overview. This file covers what an agent needs on top of
that.

## The pieces

| File | Role | Goes where |
|---|---|---|
| `client/presenter-master.js` | Laptop side. Returns at once unless the URL has `?master`, or `?presenter` (the tablet's copies, where it runs as a mirror). | Every deck, or the shared template |
| `client/presenter-polls.js`, `client/presenter-polls.css` | Laptop side of polls, the board and reactions. An ES module and its stylesheet, which `presenter-master.js` loads only with `?master` and `questionsKey`, or in a mirror | Beside `presenter-master.js` (or `pollsScript`, `pollsStyle`) |
| `client/presenter-drive.js` | Laptop side of Drive and ink: applies the tablet's strokes and steps, sends what is drawn. An ES module, loaded only with `?master` and `questionsKey`, never in a mirror | Beside `presenter-master.js` (or `driveScript`) |
| `client/presenter.html` | Tablet side. Loads the deck twice in iframes (`?presenter`) and drives them; questions, word approval, poll counts, the board, "Lost?", reactions, Reset and Reload. | Same origin as the decks |
| `client/presenter-driver.js`, `presenter-ink.js`, `presenter-mirror.js` | Tablet side of Drive, of the laptop's ink, and of what its copies draw as mirrors; loaded by `presenter.html` | Beside `presenter.html` |
| `client/presenter-config.js` | Public settings, generated by `tools/make-channel.js` | Next to `presenter.html`, loaded by decks too |
| `client/ask.html` | The audience's page: questions, live polls, the board, reactions, "Lost?" (optional) | Anywhere; it only needs the config |
| `client/vendor/qr-studio.js` | The QR code library, loaded by the laptop only for a `.question-qr` | Beside `presenter-master.js` (or `qrStudio`) |
| `client/vendor/chalkboard/` | rajgoel's chalkboard plugin, changed (its README says how); Drive and ink need this copy | Loaded by the deck, as any plugin |
| `server/relay.js` | Socket.IO relay; any reveal/multiplex server works for the presenter view, but questions need this one | A host with TLS |

The protocol is reveal/multiplex's. The master emits
`'multiplex-statechanged'` with `{ socketId, secret, deck, state }`, where
`socketId` is the channel id, `state` is `Reveal.getState()` and `deck` is the
deck's path without `?master`. If `sha256(secret) === socketId`, the relay
re-emits the message, minus the secret, under the event name `socketId`.
It passes on anything else the message carries untouched (the laptop adds
`slides`, its slide count; `chalkboard` and `chalkboardGrid`, the
chalkboard's theme and grid; and `screen`, what its screen shows besides:
`indexf`, its own fragment index with the overlay steps; `qrHidden`; `pen`,
the pen's palette while it is in use). `server/relay.js` adds one event: a client may emit `'presenter-hello'` with
the channel id to get the last message replayed.

Audience questions add three events, all to `server/relay.js` only:

| Event | Sent by | Carries | Relay checks |
|---|---|---|---|
| `'questions-open'` | the laptop, every minute, ack optional | `{ socketId, secret, code, keyHash, audience? }`; `audience` is `{ reactions: [up to 8 emoji], pace: true }` | `sha256(secret) === socketId`; the ack carries the board |
| `'questions-listen'` | the tablet, with an ack | `{ channel, key }` | `sha256(key) === keyHash`; the ack carries the code |
| `'question'` | anyone, with an ack | `{ channel, code, text, name? }` | the code, the lengths (text 280, name 40), the rate limits, and that a tablet is listening |

Accepted questions go to the tablet as `'question'` with `{ id, text, name, at }`,
where `name` is `''` unless the sender gave one (on one line; it is unverified,
so show it as what the sender typed, never as an identity).
The ack's `reason` on refusal is one of `closed`, `code`, `invalid`, `slow`,
`busy`, `offline` or `key`.

Polls add six more, also `server/relay.js` only. Every poll has
`{ id, kind, prompt, instructions }` (`instructions` optional: one line telling
the audience what to do, `''` if none), plus, by kind, what it takes and the
answer (`value`) a phone sends:

| `kind` | Definition adds | A phone's answer |
|---|---|---|
| `'choice'` | `options` (2–12 labels); `picks` (how many may be chosen; omitted for 1); with `picks`, `exclusive` (an option's index, "None of them", say, chosen only on its own; omitted for none) | an option's index; with `picks`, a list of 1–`picks` distinct indices, `exclusive` only alone |
| `'number'` | `min`, `max` (integers, `max - min` ≤ 1,000,000), `unit` | an integer from `min` to `max` |
| `'scale'` | `statements` (1–12), `min`, `max` (`max - min` ≤ 10), `labels` (the two ends) | a list: an integer from `min` to `max` per statement |
| `'premises'` | `statements` (2–12), `conclusion` (its index, default the last), `labels` (default `['Accept', 'Reject']`) | a list: 1 (accept) or 0 (reject) per statement |
| `'ranking'` | `options` (2–10) | a list of every option's index, first choice first |
| `'words'` | `entries` (1–5 per phone), `moderated` (default true), `filter` (default true) | a list of up to `entries` texts of ≤ 30 characters; `[]` withdraws |
| `'self-others'` | `options` (2–6, default `['Yes', 'No']`), `target` (default 0), `others` (the second question) | `[k, p]`: the phone's own option, and its guess, 0–100, at the percentage of the room choosing `options[target]` |
| `'points'` | `options` (2–10), `total` (2–1000, default 100), `unit` | a list: the points given each option, adding up to `total` |
| `'grid'` | `items` (1–8), `min`, `max` (default 0 and 10, `max - min` ≤ 100), `x` and `y` (each axis's two ends) | a list: `[x, y]` per item, each from `min` to `max` |
| `'pin'` | `image` (an `https:` URL, ≤ 500 characters), `alt` | `[x, y]`, each 0–1000: thousandths of the image's width and height |

| Event | Sent by | Carries | Relay checks |
|---|---|---|---|
| `'poll-open'` | the laptop, with an ack | `{ socketId, secret, poll }` | the secret and the poll; the ack carries the tally |
| `'poll-close'` | the laptop | `{ socketId, secret }` | the secret |
| `'poll-results'` | the laptop, with an ack; or the tablet | `{ socketId, secret, id }`; `{ channel, key, id }` | the secret, or the questions key; the ack carries that poll's tally (the laptop then also gets its updates; the tablet has them already) |
| `'audience-join'` | a phone, with an ack | `{ channel, code }` | the day's code (questions must be open); the ack carries the open poll or `null` |
| `'poll-answer'` | a phone, with an ack | `{ channel, code, id, value, voter }` | the code, that `id` is open, the value against the kind, the rate limits |
| `'poll-moderate'` | the tablet, with an ack | `{ channel, key, id, word, status }` or `{ channel, key, id, all: true, status }` | the questions key; `status` is `'shown'` or `'hidden'`; `all` sets every pending word |
| `'board-share'`, `'board-remove'` | the tablet, with an ack | `{ channel, key, text }`; `{ channel, key, id }` or `{ channel, key, all: true }` | the questions key; the text as for a question |
| `'reset'` | the tablet, with an ack | `{ channel, key }` | the questions key; see "Rounds and reset" below |
| `'driver'` | the tablet, with an ack | `{ channel, key, from, seq, at: { h, v, f }, ops }` | the questions key; at most 400 `ops`, 40 batches a second; see "Driving from the tablet" below |
| `'ink'` | the laptop | `{ socketId, run, at: { h, v, f }, ops }` | a connection in `'master:' + channel`; at most 200 `ops`, 40 batches a second; see "Ink, to the tablet" below |
| `'ink-slide'` | the laptop | `{ socketId, run, at, n, slide: { h, v[, f] }, part, parts, mode, durations, notes, board }` | likewise; at most 400 events a part, 500 parts, 200 parts a second |
| `'ink-want'` | the tablet | `{ channel, key, at }` | the questions key; five a second |
| `'board-vote'` | a phone, with an ack | `{ channel, code, id, voter, up }` | the code; one vote per `voter` per question; `up: false` takes it back |
| `'reaction'` | a phone, ack optional | `{ channel, code, emoji }` | the code; `emoji` one of the deck's reactions; one per 0.8 s per connection |
| `'pace'` | a phone, ack optional | `{ channel, code, voter, lost }` | the code; that the deck has the pace signal on |

Phones in the audience get `'poll'` with the poll (no tally) when one opens
and `null` when it closes. The laptop, and the tablets in the questions room
(whose copies of the deck draw the laptop's charts), get `'poll-tally'` as answers arrive,
at most every 300 ms: `{ id, total }`, plus `counts` (per option, or per value
from `min`) for choice and number polls, plus `answers`, a list of
`[alias, answer]`, for every kind but words, or `words`, a list of
`{ word, n }` of the shown words only, for words. `voter` is a random id the
phone keeps, so one phone counts once and may change its answer; the alias is
a hash of it with the channel and a salt made fresh each run, the same for a
phone across a channel's polls (so before-and-after can be compared) but not
traceable to the phone. The tablet (in the questions room) gets
`'poll-words'` `{ id, prompt, moderated, open, total, words }`, each word
`{ key, word, n, status }` with `status` `'pending'`, `'shown'` or `'hidden'`,
whenever a word cloud opens, closes or changes, and on `'questions-listen'`.
Each word may also carry `caught: true`: the relay's word filter (on unless
the poll has `filter: false`) found a swear word or slur in it, and holds it
for the tablet even in an unmoderated cloud. A held word is never refused, so
a false alarm costs one tap. The phone's ack for a word cloud carries `held`,
how many of its words are not on the screen.

The tablet also gets `'poll-count'` for the latest poll as it opens, closes
and gains answers: `{ id, kind, prompt, open, total }`, plus `options` and
`counts` for a choice poll, or `median`, `mean` and `unit` for a number poll.
For a number poll wider than 1000 values the laptop's tally has no `counts`
(the `answers` carry everything).

**Driving from the tablet.** `'driver'` carries strokes for the deck's
chalkboard plugin (rajgoel's: its pen on the slide, mode 0, and its
chalkboard, mode 1) and steps: each op is one of `draw` (`mode`, `board`,
`color`, `fromX`, `fromY`, `toX`, `toY`, in the deck's own units, up to a
million: the chalkboard scrolls down without end), `erase` (`mode`, `board`,
`x`, `y`), `clear`, `scroll` (mode 1 only, `board`, `y` ≥ 0: how far down
the chalkboard is shown), `theme` (`chalkboard` or `whiteboard`), `grid` (`true` or `false`: shown or hidden), `showChalkboard`, `closeChalkboard`, and the
steps `next`, `prev`, `left`, `right`, `up`, `down` (those four as
reveal's own controls), `overview` (reveal's toggle), `question` (the deck's question button, `#question-qr-button`) and `goto` (`h`, `v`: a slide chosen in the overview, which closes it). The relay rebuilds each from those fields alone (`driverOp`;
anything else, the plugin's `init` among it, is dropped) and sends
`{ from, seq, at, ops }` as `'driver'`, with an ack, to the room
`'master:' + channel`, which a connection joins by sending a position with
the secret. The tablet's ack is the laptop's own (`{ ok: true, dropped }`),
or `no-laptop`, or `timeout` after 3 s; with two laptops on a channel, the
first that answers. The laptop applies a batch only if it is still on the
slide `at` (the step, with a plugin that keeps writing for each step; else
counts it `dropped`), ignores a `seq` it has
already applied from that `from`, and hands each op to the plugin as one of
its own `'received'` messages. Nothing is kept.

**Ink, to the tablet.** The other way, so that the tablet's copy of the
slide shows what the laptop's screen does. `'ink'` is each thing drawn on
the laptop's deck as the plugin announces it (its `'broadcast'` messages,
the kinds `driverOp` takes but the steps, and `resetSlide`), and what a
tablet's Drive drew there, numbered (`n`, from 1 in each load of the laptop's
page, which has its own `run`: 8–32 hex digits), with `from`, the tablet
page's id, on what a tablet drew; `at` is the laptop's position. The relay
rebuilds each op as `driverOp` does (`inkOp`) and sends `{ run, at, ops }`
to `'q:' + channel`, the room of the tablets holding the questions key. When
a tablet asks (`'ink-want'`, which goes to `'master:' + channel` as
`{ at }`), and whenever the laptop's page loads or reconnects, the laptop
sends `'ink-slide'`: its slide's drawings so far, the events as the plugin
keeps them (`draw` with `color`, `x1`, `y1`, `x2`, `y2`; `erase` with `x`,
`y`; `scroll` with `y`; `clear`, `selectboard`, `open`, `close`; each with
`time` and `board`), the pen's (`notes`) and the chalkboard's (`board`), in
parts of 400 events (a message may be 64 KB at most), with the last number
sent (`n`), whether the chalkboard is open (`mode`) and each canvas's
`durations`. The relay rebuilds each event (`inkEvent`) and sends the part on
to `'q:' + channel` without `socketId`. Only a connection in
`'master:' + channel` may send either: one that proved the secret with a
position. Nothing is kept.

**Rounds and reset.** The `'poll'` a phone is sent carries `round`, a random
token made whenever the relay starts keeping a poll (first opened, its
definition changed, lapsed, after a restart or a reset): a phone should
remember its answers by `id` and `round`, so that it never shows as given an
answer the relay has forgotten. `'reset'` from the tablet forgets the
channel's polls (their answers and the versions dealt), its board and its
pace signal, as a restart would for that channel alone; questions stay
open. A poll open at the time opens again, empty, in a new round, sent to
the phones (versions dealt afresh, in the room's order). Pending throttled
sends are cancelled, and the laptop (`'results:'` room) and the tablet are
sent `'reset'` (no payload) before the empty board, the pace count (0) and
the open poll's empty tally and count.

**The board** (upvoted questions): a question still reaches only the tablet;
the tablet may *share* one (`'board-share'`), which the relay then keeps,
without the sender's name, for three hours or until the tablet takes it down.
Phones, the tablet and the laptop get `'board'` `{ items }`, each
`{ id, text, votes, at }`, most votes first, whenever it changes; phones and
the laptop also in `'audience-join'`'s and `'questions-open'`'s acks.

**Reactions and the pace signal** are switched on by the laptop's
`questions-open` (`audience`), and phones learn them in `'audience-join'`'s ack
and, when they change, from `'audience'`. A reaction goes to the laptop and the
tablet as `'reaction'` `{ emoji }` and is kept nowhere. The pace signal goes to
the tablet alone, as `'pace'` `{ lost, audience, window }`: how many phones
said they were lost in the last `window` ms (two minutes), out of how many are
on the ask page.

## How the laptop's modules fit in

The relay's side is above; `README.md` has the markup (`<live-poll>`,
`<poll-results>`, `<qa-board>`, `<question-qr>`, `<question-code>`, or the
older `.poll`, `.poll-results`, `.qa-board`) and the settings. What an agent
needs besides:

- **Custom elements.** Before anything else runs, `presenter-master.js`
  gives each custom element the older markup's class, and its attributes
  again as `data-*` (a `<live-poll>`'s `name` is its `data-poll`; a
  `<poll-results>`'s `overlay` is a class), and everything after works on
  that. It does so only with `?master` or `?presenter`; elsewhere the elements
  stay empty and inline. It warns in the console about one written
  `<live-poll … />`, which swallows the rest of its slide. A `<live-poll>`'s
  `<template>`s are its versions.
- **Loading.** `presenter-master.js` stays the only script a deck includes.
  With `?master`, a valid secret and `questionsKey` (and unless `polls:
  false`), it appends `<link rel="stylesheet">` for `presenter-polls.css`
  and, once that has loaded or failed, calls the default export of
  `import('presenter-polls.js')` with an object holding what the module
  needs: `config`, `mirror`, `secret`, `channel`, `audience` (the reactions
  and pace sent with `questions-open`), `replyMs`, `deck()`, `isReady()`,
  `broadcast()`, `setStateFilter(fn)`, `sharedState()` (the position as the
  tablet is sent it), `onSocket(fn)`, `onQuestionsOpened(fn)`, `reconnect()`,
  and, for a mirror, `want(ids)` and `mirrorReady(handlers)`. Unless `drive:
  false`, it also imports `presenter-drive.js` the same way, never in a
  mirror. Nothing goes on `window` but, in a mirror, `presenterMirror`. The
  URLs default to beside `presenter-master.js` (`document.currentScript`), so
  the files travel together.
- **The mirror.** The tablet loads its copies with `?presenter`. There, with
  `questionsKey` and without `?master`, `presenter-master.js` opens no socket,
  has no secret and derives no code, and defines `window.presenterMirror`
  synchronously (the poll module arrives later by import): `tally(t)`,
  `board(b)`, `reaction(r)`, `reset()`, `code(c)`, `screen({ qrHidden, pen })`,
  `sync()`, and a writable `want`, which the tablet sets and the copy calls
  with the ids of the polls on its slide. `code` and `screen` apply at once
  (`code` is ignored where the deck fixes its own); `tally`, `board`, `reset`
  and `sync` wait for the module; a reaction before then is dropped. The
  tablet's `presenter-mirror.js` feeds it from the relay (the tallies, which
  the relay sends the questions room too, `poll-results` with the key, the
  board, reactions, resets) and from the laptop's `screen`, and waits up to
  15 s for a copy's `presenterMirror`.
- **The position's extra fields** (`slides`, `chalkboard`, `chalkboardGrid`,
  `screen`) are sent with every broadcast, and at once when the board's theme
  or grid changes, the QR code is hidden or shown, or the pen is picked up.
- **Staying connected.** Safari on one university network lost its connection
  every minute or so without a word, and socket.io's heartbeat noticed only
  after 45 s. So the laptop asks the relay for a reply every 5 s and with each
  poll it opens (`replyMs`), and starts a new connection (WebSocket first)
  when none comes; after a reconnect it closes a poll it has since left. The
  ask page rejoins every 10 s while in view, and on becoming visible.
- **Timing.** The module arrives after reveal.js has usually started, and
  copes either way: it checks `isReady()` and also listens for `ready` on
  `.reveal`; it registers its socket handlers through `onSocket()` and, if
  the socket is already connected, syncs at once. On every (re)connect it
  forgets which poll it opened and opens the slide's again, since the relay
  may have restarted.
- **Overlays.** A `.poll-results.overlay` becomes a fragment
  (`fade-in-then-out`, marked `data-master-only-step`) in the `?master` copy
  only. If reveal.js has not yet numbered the slide's fragments, it numbers
  the step in document order with the rest. If it has (the usual case: the
  module loads late), the module numbers it after the last fragment before it
  in the document and moves the later ones up one, and, if the deck was opened
  part-way through that slide, re-applies the position so the same fragments
  show. `setStateFilter()` then subtracts the master-only steps already passed
  from `indexf` in every broadcast (design rule 18). The tablet's mirroring
  copies have the steps too, and take the laptop's own index from
  `screen.indexf`; any other follower takes `state`.
- **Settings that were server-side variables** in the PHP course this was
  ported from are `PresenterConfig` options: `reactions`, `pace` (off unless
  `true`, as the course has it since 17 October), `pollPill`,
  `pollPillPosition`, plus `webAwesome` and `d3Cloud` for the libraries.
  Since 10 November also `drive`/`driveScript`, `questionButton`/
  `questionButtonIcon` and, on the tablet, `hideInNext`. The ask page and the
  tablet read the same file, so one config serves all three pages.
- **The question button** (the course's `question-button.js`, in
  `presenter-master.js`): a button on a customcontrols toolbar (`#customcontrols
  > ul`; no toolbar, no button) that toggles `body.question-qr-hidden`. Only on
  localhost or in a browser marked `localStorage['presenter-lecturer']` (set
  by `?master`, and by a tablet whose key was accepted), never under
  webdriver. In a plain view it appears only with the server-side variant
  (`config.secret`), since its reload into `?master` must carry the secret. A
  mirror marks it as the laptop's and never acts on a tap; Drive's `question`
  op presses it.
- **Drive** (`presenter-drive.js`): applies a `'driver'` batch only if the
  laptop is still on its slide, ignores a repeated `seq`, and hands each op to
  the chalkboard plugin as one of its own `'received'` messages, after the
  plugin's settling wait on a new slide. Without the plugin, steps still work
  and strokes count as dropped. It sends `'ink'` for everything the plugin
  announces and what a tablet drew (with `from`), and `'ink-slide'` on load,
  reconnect and `'ink-want'`.
- **Libraries.** The ask page loads Web Awesome 3.14.0 from jsDelivr
  (`webAwesome` overrides the `dist-cdn` base): its theme tokens
  (`styles/themes/default.css`, not its native-element styles) and
  `webawesome.loader.js`, which defines each `wa-*` element as it appears.
  The loader finds its components from its own `<script src>`, which must end
  in `webawesome.loader.js` with no query string; its `data-webawesome`
  attribute keeps only a path, so it cannot point at another origin. The
  laptop loads d3-cloud 1.2.9 (a classic script, `d3.layout.cloud`) only for
  a deck with a `data-kind="words"` poll. To serve both from the user's own
  site, copy those directories there and set the two options.
- **Styling.** `presenter-polls.css` takes its colours from the reveal.js
  theme through custom properties on `.reveal` (`--poll-accent`,
  `--poll-text`, `--poll-card`, `--poll-highlight`, `--poll-colour-1` to
  `-8`). Restyle by setting those in the deck's CSS, not by editing the file.

## Integration procedure

### 1. Survey the project first

Find out, from the code where possible:

- **How decks are built:**
  - plain HTML files;
  - a shared template (PHP, Jinja, Hugo, Eleventy, …);
  - generated by a tool (Quarto, reveal-md, Slides.com export).

  With a template, the two script tags go in the template once. With a
  generator, find its hook for extra scripts. Quarto, for example, has
  `include-after-body`.
- **Whether `window.Reveal` exists:**
  - `<script src=".../dist/reveal.js">` plus `Reveal.initialize()`: yes.
  - ES modules (`import Reveal from 'reveal.js'; const deck = new Reveal()`):
    no. Add `window.Reveal = deck;`. The presenter's iframes need it, not just
    the master script.
  - Several decks on one page (`embedded: true`): not supported.
- **The reveal.js version.** 4, 5 and 6 share the API used here. 6 moved
  plugins from `plugin/<name>/<name>.js` to `dist/plugin/<name>.js`.
- **Where decks are published,** and whether a directory such as `/presenter/`
  can sit on the same origin. It must: the presenter page reads and drives
  `contentWindow.Reveal`, which a browser allows only same-origin.
- **Whether the user presents from a local copy or the published site.** The
  tablet always loads the *published* copy, so the two must have the same slide
  structure, and the same path, or `deckUrl` must map between them.
- **Whether a relay already exists:** a reveal/multiplex URL in their decks,
  or a server they run.

### 2. Ask only what the code can't tell you

Typically:
- which relay to use: an existing one, or deploy `server/` (and to which host);
- how the site is deployed.

Do not deploy, change a server, or create DNS records without explicit
confirmation. These are outward-facing actions.

### 3. Make the channel

```
node tools/make-channel.js <relay-url> --write <their>/presenter/presenter-config.js
```

For audience questions with a QR code, add `--ask <public URL of ask.html>`; it
becomes `askUrl`, and the laptop draws the code into any `.question-qr`
element. It must be the public address, even if the user presents from
`localhost`, since phones open it.

Give the user the printed secret, and their laptop URL in the form
`…/deck.html?master=<secret>`. **Never write the secret into a file that is
published or committed.** The one sanctioned exception is the server-side
variant below.

### 4. Install and wire up

1. Copy `presenter.html` and `presenter-master.js` next to the generated
   `presenter-config.js`. `presenter.html` loads the config by relative path,
   so keep the three files together. With questions, add `ask.html`,
   `vendor/`, `presenter-polls.js`, `presenter-polls.css` and
   `presenter-mirror.js` to the same directory, and for Drive
   `presenter-drive.js`, `presenter-driver.js` and `presenter-ink.js`. Ask
   whether the user wants reactions (`reactions` in the config) and "Lost?"
   (`pace: true`; off by default).
   For Drive and the laptop's writing on the tablet, the deck needs the
   chalkboard plugin from `vendor/chalkboard` (its `style.css`, `plugin.js`
   and `RevealChalkboard` among the plugins; it uses Font Awesome's free icons
   for its handle). If the deck already has rajgoel's chalkboard, replace it
   with this copy: the unchanged plugin has none of `slideDrawings()`,
   `setSlideDrawings()`, `slideTime()` or `boardOpen()`, and keeps writing per
   fragment step. Set its `transition` short (100 ms): writing sent from the
   tablet waits that long on a new slide.
2. Add `<script src=".../presenter-config.js">` and
   `<script src=".../presenter-master.js">` to each deck or the template,
   anywhere after reveal.js is loaded. They work before or after
   `Reveal.initialize()`.
3. If the deck's plugins draw their own UI that `Reveal.configure()` can't hide
   in the presenter's copies, add selectors to the config: `hideInFrames` for
   what belongs in neither copy (default: the menu plugin's open panel), and
   `hideInNext` for controls that belong on the current slide, as projected,
   but not on the next (default: the menu's button, customcontrols, the
   chalkboard's handle and palettes).

### 5. Verify

Do all of this before calling the work done:

- **A deck opened without `?master` must be unchanged.** Compare the rendered
  HTML before and after, or check the network log: no request may go to the
  relay. Published decks are what the audience and the public see. A
  `?presenter` copy must contact no relay either.
- **Laptop with `?master` plus a tablet-sized window.** Use one window around
  1180×820 *and* one around 820×1180: portrait is where the narrow "Next" pane
  trips reveal.js's scroll view. Check the current slide, the next fragment,
  the notes, and catching up after reloading the tablet page.
- **The automated tests.** `tools/e2e-test.js` and `tools/polls-test.js` run
  against `example/` and can be pointed at a real relay (`RELAY_URL`) or
  another reveal.js version (`REVEAL_VERSION`); `laptop-test.js`,
  `tablet-test.js`, `drive-ink-test.js`, `ask-test.js` and
  `chalkboard-test.js` cover what came on 10 November (README's Testing). To
  test the user's own deck, adapt their `DECK` and steps. Keep their timed
  polling (see the testing traps below).
- **Drive, if the deck has the chalkboard.** On the tablet in a 820×1180
  window, Drive, write with a pen (pointer events with `pointerType: 'pen'`,
  as `tablet-test.js` sends them) and see it on the laptop; write on the
  laptop with the mouse and see it on the tablet's current slide.
- **Polls, if the deck has any.** With `?master`, step onto each poll slide
  with a phone-sized window on `ask.html`; answer, and see the chart. Without
  `?master` (or `?presenter`), check that the deck requests nothing called
  `presenter-polls` or `presenter-drive` and that every `.poll`,
  `.poll-results` and `.qa-board` stays empty.
- **Hunt for leaked secrets.** Grep the user's repository and the deployed
  files for the secret.

## Design rules — keep these when adapting the code

Each of these was learned the hard way. They look like simplification
opportunities and are not.

1. **Opt-in master; never make a published deck a follower.** reveal.js's own
   multiplex client mode makes every copy of a deck follow the master. For a
   public deck, that yanks every viewer (students reading it during the
   lecture, say) through the slides in step with the speaker. Here only
   `presenter.html` follows, and decks do nothing unless `?master` is present.
2. **Heartbeat.** The reveal/multiplex relay keeps no state, so a tablet that
   sleeps, reconnects or opens late learns the position only from the next
   message. The master re-broadcasts every 3 s. `server/relay.js` also replays
   the last message on `'presenter-hello'`; keep the heartbeat anyway, so the
   client works with any relay.
3. **Load the Socket.IO client asynchronously in the master.** A synchronous
   `<script src>` pointing at an unreachable relay would stall the deck in
   front of an audience.
4. **Listen for reveal's events on the `.reveal` element, not with
   `Reveal.on()`.** The master script often runs before `Reveal.initialize()`.
   reveal's events bubble from `.reveal`, so DOM listeners work whatever the
   order.
5. **Lay the iframes out at a fixed size (1280 px wide, at the deck's own
   aspect ratio) and scale them down with a CSS transform.** reveal.js 5+
   switches any deck whose window is narrower than `scrollActivationWidth`
   (435 px) into *scroll view*. There, `setState()` and `next()` scroll instead
   of jumping, and the position updates asynchronously, so the "Next" pane
   shows the wrong fragment. On a portrait iPad that pane is about 390 px wide.
   Setting `Reveal.configure({ scrollActivationWidth: null })` afterwards does
   **not** leave scroll view once it is active. Sizing the iframe to its box is
   the bug; don't "fix" the layout that way.
6. **Make the frames passive:**
   - `keyboard` and `touch` off;
   - on the *next* copy, `controls`, `progress` and `slideNumber` off too, and
     the plugins' controls hidden (`hideInNext`); the *current* copy keeps the
     deck's own controls, lit as the laptop's are, since it shows what the
     projector does (since 22 October in the course);
   - `transition: 'none'`;
   - `autoPlayMedia: false`, and pause and mute all media after every move;
   - `pointer-events: none` on the iframes, except the current copy in Drive,
     where a tap (never a palm) reaches the deck's own controls;
   - `hash: false, history: false`. Otherwise every move adds an entry to the
     tablet's back-swipe history.
7. **Compute the "next" pane by applying the state and then calling `next()`
   on the second frame.** That respects fragments, vertical stacks and custom
   `data-fragment-index` orders without reimplementing reveal's navigation.
8. **When the laptop has the screen blanked or the overview open, show it as
   the laptop has it on the current slide, plus a badge, and keep the slide on
   the next.** The speaker needs to see both what the audience sees and where
   they are. (Before 22 October the current slide showed the slide with a
   badge alone; in Drive, the overview is now where a tap chooses a slide.)
9. **Re-render when a frame has drifted, not only when the state changes.**
   iPad Safari can reload an iframe in the background, leaving it on slide 1.
   `render()` compares each frame's actual position with where it last put it.
10. **Validate the deck path from the relay** (it must be a same-origin path)
    before loading it in an iframe.
11. **Don't serve the relay's directory as static files.** reveal/multiplex's
    `index.js` does (`express.static(process.cwd())`), which publishes anything
    stored there. On one real server that included a secrets file and `.git/`.

For audience questions:

12. **Questions are transient.** The relay forwards each one to the tablet's
    open connections and keeps nothing; it never logs question text. With no
    tablet listening, the question is *refused*, not queued, and the student is
    told. Don't add a buffer "for reconnects": that is storage, and the user
    asked for none.
12a. **Polls keep answers, and only those.** Each phone's current answer
    under its random id, in memory, forgotten three hours after the poll was
    last opened; never written or logged. Answers go to the laptop (proving
    the secret) under aliases, never the phones' ids; a word cloud's words go
    first to the tablet (proving the key) and reach the laptop only once
    shown. (The user chose this so that a laptop reload loses nothing,
    results can appear on a later slide, and free text is never projected
    unseen.) A poll in versions also keeps which version each phone was
    dealt, with the poll and for as long, so that a reload brings back the
    same one; a phone is sent only its own version, never the others or
    their names. The tablet's `'reset'` forgets all of it for its channel
    at once (for a rehearsal, say); it only ever removes state, never keeps
    more.
12b. **The board keeps only what the tablet shares.** Questions still go
    only to the tablet; the lecturer chooses which to share for upvoting, and
    the relay keeps those, without names, for three hours. Never put an
    incoming question on the board automatically.
13. **Tie the code and the key to the presenter secret.** Only a client that
    proves the secret may set a channel's code and accepted key hash.
    Otherwise anyone with a channel of their own could open questions on
    yours.
14. **Show questions with `textContent`, never `innerHTML`.** They are
    anonymous input arriving on the speaker's device. The same goes for
    everything else from the audience (a word cloud's words, the board) and
    from the deck (a poll's prompt and options, sent through the relay to
    every phone).
15. **Don't rate-limit by IP address alone.** A lecture hall on eduroam can sit
    behind a handful of public addresses. Limit per connection and per
    channel, with only a generous per-address cap. Behind nginx, take the
    address from `X-Real-IP`, which is safe because the relay listens on
    localhost only.
16. **The code must exist only on the laptop.** It is derived from the secret
    and the date, so the published deck cannot show it, and it changes daily.

For polls:

17. **Only the `?master` copy, and the tablet's mirrors of it, load poll code
    or draw anything.** The published deck keeps its `.poll`,
    `.poll-results` and `.qa-board` empty. An inline chart therefore leaves an
    empty space there; that is the price of rule 1, not a bug to fix by
    drawing in every copy (which would need every copy to connect). The
    tablet's copies draw only because the tablet page, which holds the key,
    hands them what to draw: a mirror never connects, never knows the secret
    and never derives the code.
18. **An overlay's step exists only on the laptop and in its mirrors, so leave
    it out of the broadcast's `state`.** Otherwise a follower that is not a
    mirror runs one step ahead: with the chart up, it shows the fragment after
    the chart. The difference is invisible when the overlay is the slide's
    last step (the copy clamps to its last fragment), which is why the demo
    slide has a fragment after it. The laptop's own index goes besides, as
    `screen.indexf`, for the mirrors, which have the step.
19. **A word cloud's words reach the screen only as shown.** In a cloud the
    deck marks `moderate="on"`, every word waits for the tablet; otherwise
    words are shown at once (the default since 18 October, as in the course),
    but never one the relay's filter catches, which waits for the tablet. The
    laptop draws only shown words (the relay enforces it; don't add a
    shortcut), and the tablet can hide any of them.
20. **Answers are matched across polls only by the relay's aliases.** Before
    and after compares by alias; never send, store or show the phones' own
    voter ids anywhere else.

## Server-side templated sites (PHP and similar)

(For questions, a PHP site can compute the day's code server-side, for
example `sprintf('%04d', hexdec(substr(hash('sha256', $secret . ':questions:'
. date('Y-m-d')), 0, 8)) % 10000)`, and emit it only on the `?master` copy.)

The first version of this ran on PHP decks. There, a server-side include
emitted the master script only when `?master` was present, and the secret
lived in a PHP config file. That file is executed rather than served, so it is
never readable as source.

In a template, that means:
- emit `window.PresenterConfig.secret = '<secret>'` inside an
  `if (isset($_GET['master']))` (or equivalent) block, before
  `presenter-master.js`;
- the laptop URL is then just `?master`.

Two cautions:
- Anyone who adds `?master` to a published deck receives the secret in the
  HTML. The worst they can do with it is steer the speaker's tablet.
- Templated decks are often frozen into archive copies. Guard the include so a
  copy without the config file still renders, e.g. `is_file()` in PHP.

## Testing traps

- **Puppeteer's `page.waitForFunction()` polls on animation frames by default.
  A background tab gets none,** so it times out however correct the page is.
  With a "laptop" and a "tablet" open, one is always in the background. Pass
  `{ polling: 200 }`.
- **Clicks and screenshots need the page to render frames.** `page.click()`
  scrolls the element into view first, and `page.screenshot()` captures a
  frame. In one sandbox, headless Chrome 148 rendered none: both hung until
  the protocol timed out while `evaluate()` still worked. The tests click
  from inside the page (`clickIn`) for this reason; for screenshots, try
  another Chrome via `PUPPETEER_PATH`.
- **A freshly loaded frame sits on slide 1 before the presenter has
  positioned it,** so "current matches laptop" can pass by accident. Also wait
  for the presenter's own slide counter, which changes only after a render.
- **Check that a new test can fail.** The scroll-view bug passed every
  landscape check. Only the portrait run caught it, and only once the checks
  compared the "Next" pane with an oracle: a plain copy of the deck, given the
  same state and then `next()`.
- `127.0.0.1` and `localhost` are secure contexts, so `crypto.subtle` (used
  for the master's local secret check) works there. It is not available on
  plain-HTTP LAN addresses; there the check is skipped.
- **Each emulated phone needs a browser context of its own.** A phone is
  counted by a random id in its `localStorage`, so pages in one context are
  one voter: `browser.createBrowserContext()` per phone.
- **Wait for the count before checking what follows from it.** A chart can
  match the expected text on an earlier tally (two of three answers can
  already give the right winner); wait for "3 answers" first.
- **Newer Chrome blocks a page at `about:blank` from fetching `localhost`.**
  Open a same-origin page first (relay-test.js opens the relay's `/`).
- **Web Awesome components live in shadow DOM.** Type into a tag input with
  `page.$('wa-tag-input >>> input')`, then `keyboard.press('Enter')`; set a
  slider's `value` and dispatch `input`. Click a `wa-button` from inside the
  page, as everywhere else.
- **A test's web server must answer `/favicon.ico`** (204 will do). The
  browser asks for it on every page, and a 404 is logged as a console error,
  which a check for "no errors" then counts against the page.
- **A background tab gets no ResizeObserver callbacks either** (they run with
  rendering). The word cloud is laid out from a timer, so it still draws; its
  chart's `data-placed` says how many words were placed.

## Implementation traps

- **SVG presentation attributes don't take `var()`.** Set a palette colour
  with `element.style.fill = 'var(--poll-colour-1)'`, not
  `setAttribute('fill', …)`, or the shape is drawn black. A canvas can't take
  `var()` or `color-mix()` at all; resolve the colour through a probe
  element's computed `color` first.
- **reveal.js renumbers fragments only when it sorts them.** Adding
  `.fragment` after it has started puts the new step last unless it is given
  a `data-fragment-index` (see "Overlays" above).
- **The relay sends no `poll-words` when another poll replaces a word cloud**
  (only on `poll-close`). The tablet infers that the cloud has closed from a
  `poll-count` for another open poll.

## Known limitations (tell the user rather than work around silently)

The tablet controls the laptop only in Drive, which needs the questions key;
writing from it, and the laptop's writing shown on it, need the vendored
chalkboard plugin in the deck. The position, that writing, and what the
presenter's own scripts draw are mirrored; media playback, other plugins'
state and in-slide interaction are not. Same-origin and `window.Reveal` are
hard requirements. Each deck is loaded twice on the tablet.

Polls need audience questions on (phones join with the code), draw only on
the laptop and the tablet's copies, and need `server/relay.js`. A pin poll's
picture must be reachable by the phones over `https`. Before and after
compares only phones that answered both, and only while the relay keeps
running (aliases are salted afresh at each start).

The project's tablet keeps questions transient (rule 12): unlike the PH226
course's iPad, it has no question log, and the ask page takes no name.
